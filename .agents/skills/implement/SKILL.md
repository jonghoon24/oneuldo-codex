# 스펙 구현

프로젝트 루트의 `SPEC.md`를 기준으로 기능을 구현하고, 완료 조건별 실제 확인 근거를 보고한다. `$implement` 등 사용자의 명시적인 호출이 있을 때만 사용한다.

## 1. 읽고 계획하기

- 적용되는 `AGENTS.md`, `SPEC.md`, 관련 코드, 기존 E2E 테스트와 Playwright 설정, 실행 스크립트를 읽는다. 작업 중인 변경도 확인하여 기존 사용자 작업을 보존한다.
- `SPEC.md`가 없거나 핵심 동작·완료 조건이 정해지지 않았다면 추측해 구현하지 말고 필요한 내용을 묻는다. 스펙의 '안 하는 것'을 구현 범위에 넣지 않는다.
- 구현 전에 다음 내용을 갖춘 계획을 대화에 제시한다. 별도 계획 파일을 만들 필요는 없다.
  - 구현 방법: 바꿀 파일·함수와 상태·데이터 흐름, 기존 코드 재사용 방법, 필요한 경계·오류 처리.
  - 남길 E2E 테스트: 기존 테스트로 확인되는 동작, 추가·수정할 시나리오와 기대 결과, 그 테스트를 남기는 이유.
  - 완료 조건별 확인 방법: SPEC.md의 각 완료 조건을 식별하고, 사용할 E2E 시나리오 또는 Playwright MCP 조작·관찰 등으로 어떻게 충족 여부를 판단할지 대응시킨다. 스펙에 번호가 없으면 검토용 번호를 붙이되 이를 위해 스펙을 수정하지 않는다.
- 현재 모드가 파일 수정을 허용하지 않으면 계획과 검토까지 진행하고, 구현은 실행 가능한 모드로 전환된 뒤 이어간다. 모드 제한을 구현 승인 요청으로 대신하지 않는다.

## 2. plan-reviewer 검토받기

- 프로젝트 서브에이전트 `plan-reviewer`를 호출한다. 설정은 프로젝트 루트의 `.codex/agents/plan-reviewer.toml`에 있다.
- 계획 전문, 프로젝트 루트, `SPEC.md`와 `AGENTS.md`, 관련 코드·테스트의 위치를 전달한다. 에이전트가 자료를 직접 읽고 읽기 전용으로 검토하도록 한다.
- 계획에서 바꾸기 어려운 결정의 필요성, 스펙 누락·범위 초과, 기존 구조와 설계의 복잡성, 테스트와 완료 확인 방법을 검토받는다. 각 지적에 계획 위치와 파일·줄 번호 근거를 포함하고, 사람이 결정할 사항에만 `[사람 확인]`을 붙이도록 한다.
- 검토 결과가 올 때까지 기다린다. 에이전트 설정이나 호출 도구가 없어 실제 검토를 받을 수 없다면 제한을 알리고 해결을 요청한다. 자체 검토를 에이전트 검토 결과로 대신하거나 검토 단계를 생략하고 구현하지 않는다.

## 3. 지적 판단과 계획 확정

- 각 지적을 스펙·프로젝트 지침·코드 근거와 대조하여 타당성을 판단한다. 타당한 지적은 계획에 반영하고, 반영하지 않는 지적은 근거와 이유를 남긴다. 에이전트 의견을 무조건 수용하지 않는다.
- `[사람 확인]` 지적이 하나라도 있으면 구현 전에 사용자가 결정할 내용을 묶어서 질문하고 답을 기다린다. 각 질문에는 계획의 해당 부분, 근거, 필요한 결정과 선택의 영향을 적는다. 반영하지 않으려는 `[사람 확인]` 지적도 그 이유를 함께 제시하여 확인받는다.
- 이 확인은 `plan-reviewer`가 표시한 스펙·사용자 동작·새 라이브러리·저장 형식 관련 미결정 사항을 해소하기 위한 것임을 설명한다. 이 스킬의 해당 지침을 인용하고 이 파일을 링크한다. 이미 답변·승인된 사항을 다시 묻지 않는다.
- 직접 발견한 미결정 사용자 동작이나 스펙 변경도 임의로 확정하지 않는다. 새 라이브러리 등 `AGENTS.md`가 요구하는 승인 역시 지킨다.
- 사용자 답변이 있으면 계획에 반영한다. 새로 미결정 사항이 생긴 경우에만 추가로 묻는다. `[사람 확인]`이나 별도의 필수 승인·미결정 사항이 없으면 일반적인 계획 승인을 요청하거나 멈추지 말고 구현으로 진행한다.
- 반영 후 새로운 설계 위험이나 스펙 충돌이 생겼다면 바뀐 부분을 재검토받는다. 같은 계획을 이유 없이 반복 검토하지 않는다.

## 4. 구현과 E2E 테스트

- 확정한 계획대로 관련 코드와 필요한 E2E 테스트를 작성·수정한다. 요구사항을 맞추기 위해 SPEC.md의 완료 조건을 임의로 완화하거나 바꾸지 않는다.
- E2E 테스트는 완료 조건마다 하나씩 만들지 않는다. 아래 중 회귀를 막을 가치가 큰 동작을 골라 남긴다.
  - 사용자가 자주 사용하는 주요 기능이나 작업 흐름.
  - 다른 기능과 연결되어 있어 변경 시 깨지기 쉬운 동작.
  - 잘못된 입력을 막는 동작 중 대표적인 경우.
- 테스트 하나로 완료 조건 여러 개를 검증해도 된다. 기존 테스트로 충분하면 새 테스트를 추가하지 않고 재사용한다. 기존 테스트의 구조·초기 데이터·시간대 설정을 따르며 관찰 가능한 사용자 동작과 결과를 검증한다.
- 구현 중 계획을 바꿔야 하면 이유와 영향을 기록한다. 새 사용자 결정이나 필수 승인이 필요한 변경이면 적용 전에 질문하고 기다린다. 일상적인 구현 조정은 계속 진행한다.

## 5. 완료 조건 검증

- `AGENTS.md`에 따라 `npm run lint`, `npm run build`를 실행하고, 계획에서 남기기로 한 E2E 테스트를 포함해 `npm run test:e2e`를 실행한다. 실패하면 원인을 수정하고 영향을 받는 검증을 다시 수행한다.
- 완료 조건별로 실제 결과와 기대 결과를 대조한다. E2E 통과만으로 모든 완료 조건을 통과 처리하지 않고, 각 조건에서 어떤 결과를 확인했는지 연결한다.
- E2E로 확인되지 않는 부분은 Playwright MCP로 앱을 직접 실행·접속하고 조작하여 확인한다. 필요한 개발·미리보기 서버를 실행하고, 조건에 해당하는 입력·조작과 화면·저장 결과를 관찰한다. 정적인 코드 읽기나 서버 실행 성공만으로 사용자 동작을 확인했다고 하지 않는다.
- 완료 조건 하나를 E2E와 Playwright MCP 등 여러 방법으로 확인해도 된다. `AGENTS.md`에서 요구하는 브라우저 확인도 수행한다.
- 브라우저 확인은 테스트용 브라우저·데이터로 수행하여 실제 사용자 기록을 손상시키지 않는다. 확인에 사용한 조건, 조작과 관찰 결과를 최종 보고에 남길 수 있게 기록한다.
- 도구·브라우저·환경 문제로 E2E나 Playwright MCP 확인이 불가능하면 해당 제한을 명시한다. 확인하지 못한 조건은 미확인으로 남기고, 실제 실행하지 않은 검증을 통과했다고 주장하지 않는다.

## 6. 결과 보고

다음 내용을 한국어로 보고한다.

- 구현한 동작과 중요한 변경.
- 완료 조건별 표: 조건 번호·내용, `통과` / `실패` / `미확인`, 확인 근거. 근거에는 E2E 테스트 경로·시나리오와 실행 결과, 또는 Playwright MCP에서 수행한 조작·관찰 결과를 구체적으로 적는다. 일부만 확인한 조건은 통과로 표시하지 않는다.
- 계획 검토 지적의 처리: 반영한 지적과 변경 내용, 반영하지 않은 지적과 그 근거·이유, `[사람 확인]`에 대한 사용자 결정. 지적이 없었다면 `지적 없음`이라고 적는다.
- 새로 쓰거나 고친 E2E 테스트의 경로·시나리오·남기는 이유. 기존 테스트를 재사용했다면 이를 밝힌다.
- 린트·빌드·E2E 실행 결과와 남은 검증 제한. 실패하거나 미확인인 조건이 있으면 모두 완료했다고 보고하지 않는다.
