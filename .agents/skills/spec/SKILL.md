# 기능 스펙 인터뷰

사용자가 만들 기능을 구체화하고, 구현 가능한 한국어 스펙으로 합의한다. 입력은 `$spec 습관별 주간 목표를 추가하고 싶어`처럼 만들 기능에 대한 설명이다. 오늘도의 기존 기능으로 입력을 고정하지 않는다.

## 모드 확인

- 먼저 현재 협업 모드와 대화 맥락을 확인한다. 사용자의 표현만으로 플랜 모드라고 판단하지 않는다.
- 이미 이 스킬로 인터뷰를 마치고 확정한 계획을 사용자가 실행하는 경우에는 아래의 **계획 실행**으로 진행한다. 일반 모드라는 이유로 인터뷰를 다시 시작하지 않는다.
- 새 인터뷰 요청인데 플랜 모드가 아니라면 다음 문구를 안내하고 멈춘다. 질문, 파일 작성, 구현은 시작하지 않는다.

  > 이 스킬의 인터뷰는 플랜 모드에서 진행합니다. Shift+Tab으로 플랜 모드를 켠 뒤, `$spec 만들 기능 설명`으로 다시 불러 주세요.

## 플랜 모드 인터뷰

1. 만들 기능이 입력되지 않았고 대화에서도 확인할 수 없으면, 먼저 어떤 기능을 만들지 묻는다.
2. 프로젝트의 `AGENTS.md`, 기존 `./SPEC.md`, 요청과 관련된 코드를 읽어 이미 정해진 동작과 제약을 파악한다. [형식 예시](references/SPEC.md)도 읽는다. 예시는 이 스킬을 만들 당시의 `./SPEC.md` 사본이며, 네 섹션의 구조와 구체성만 참고한다. 예시 기능을 이번 요구사항으로 간주하지 않는다.
3. 기능의 동작과 엣지 케이스를 인터뷰한다. 이미 입력이나 프로젝트에서 확인한 사실을 되묻는 뻔한 질문은 피하고, 사용자가 놓치기 쉬운 결정과 모호한 경계를 파고든다.
   - 실제 사용 상황을 제시해 서로 다른 선택이 어떤 결과를 만드는지 묻는다. 예를 들어 날짜 경계, 과거 기록 수정, 삭제 후 관련 데이터, 저장 실패 같은 문제 중 요청에 해당하는 것만 다룬다.
   - 사용자에게 의미 있는 동작을 묻고, 일상적인 구현 선택은 프로젝트 관례로 해결한다. 기존 제약과 요청이 충돌하면 그 영향을 설명하고 필요한 결정을 받는다.
   - `request_user_input`으로 한 번에 1~3개의 연관 질문을 하고, 답변에 따라 다음 질문을 정한다. 도구가 없으면 대화로 묻는다. 질문을 한꺼번에 긴 체크리스트로 나열하지 않는다.
   - 주요 사용 흐름, 상태 변화, 관련 경계·실패 상황, 제외 범위, 검증할 결과가 정해질 때까지 진행한다. 기능과 완료 조건을 바꾸는 미결정 사항을 임의로 확정하지 않는다.
4. 인터뷰가 끝나면 파일을 쓰지 않고, `SPEC.md`에 들어갈 **전체 본문**을 최종 계획의 `<proposed_plan>`에 제시한다. 단순한 작성 절차나 요약으로 대신하지 않는다.

## 최종 계획 형식

계획에는 실행 범위를 명확히 적는다.

> 이 계획을 실행하면 아래 본문으로 프로젝트 루트의 `./SPEC.md`만 생성하거나 갱신한다. 앱 구현, 의존성 설치, 다른 파일 변경, 커밋은 하지 않는다.

이어서 문서 제목과 아래 네 섹션으로 구성된 완성된 본문을 제시한다. 다른 최상위 섹션을 추가하지 않으며, 기능별 하위 제목은 사용할 수 있다.

```markdown
# [대상 기능 또는 버전] 스펙

## 목표

## 이번에 만드는 기능

## 안 하는 것

## 완료 조건
```

- **목표**: 이 기능이 왜 필요한지 사용자 입장에서 한두 줄로 쓴다. 기능 목록이나 구현 방법을 나열하지 않는다.
- **이번에 만드는 기능**: 인터뷰에서 합의한 동작, 입력 규칙, 상태 변화, 경계 조건과 실패 처리.
- **안 하는 것**: 이번에 제외하기로 한 기능이나 범위를 혼동하기 쉬운 관련 기능만 적는다. 관계없는 기능을 관성적으로 나열하지 않는다.
- **완료 조건**: 아래 규칙으로 작성한다.
  - 각 조건에 `AC-1`, `AC-2`처럼 문서 안에서 연속된 번호를 붙인다.
  - 충족 여부를 객관적으로 판단할 수 있도록 쓴다. 어떤 상황에서 무엇을 하면 어떤 결과가 나와야 하는지 쓴다.
  - 무엇이 되어야 하는지만 쓰고, 어떻게 구현하거나 테스트할지는 쓰지 않는다.
  - 주요 흐름, 상태 변경, 잘못된 입력과 오류, 데이터 유지 등 해당 기능에서 중요한 경우를 빠뜨리지 않는다. 겹치거나 지나치게 세세한 조건은 합치거나 제외한다.
  - 린트, 타입 검사, 테스트 통과처럼 매번 하는 확인은 넣지 않는다.

플랜 모드에서는 `SPEC.md`를 포함해 어떤 파일도 생성하거나 수정하지 않는다. 사용자가 플랜 모드에서 작성을 요청해도 본문을 계획으로 제시하고 실행 단계로 넘긴다. 기존 스펙이 있다면 요청에 따라 갱신할 범위를 인터뷰에서 확정하고, 유지하기로 한 요구사항까지 포함한 전체 본문을 제시한다.

## 계획 실행

- 인터뷰를 완료한 계획에 대한 실행 요청이 있고 파일을 쓸 수 있는 모드일 때만 진행한다.
- 확정한 문서 본문을 프로젝트 루트의 `./SPEC.md`에 그대로 작성한다. 계획 실행 안내나 `<proposed_plan>` 태그는 파일에 넣지 않는다.
- 확정된 본문이 대화에 없거나 중요한 결정이 남아 있다면 추측해 작성하지 않는다. 플랜 모드에서 인터뷰 또는 계획을 마무리하도록 안내한다.
- 작성 전에 현재 `SPEC.md`가 계획에서 읽었던 내용과 달라졌다면 충돌을 확인하고, 새 변경을 임의로 덮어쓰지 않는다.
- 파일 내용이 확정한 본문과 일치하는지 확인하고 작성한 경로를 알린다. 실행 범위는 `SPEC.md` 한 파일이다. 앱 코드, 스킬, 설정, 기타 문서는 수정하지 않으며 앱 구현이나 빌드·테스트·커밋도 수행하지 않는다.
